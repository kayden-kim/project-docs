# 문서 작성 규칙

`docs/` 전체에 적용한다. 하위 `AGENTS.md`는 유형별 규칙을 더한다. 충돌하면 더 가까운 지침을 따르고, 사용자 지시는 저장소 지침보다 우선한다. [용어집](#용어집) 규칙은 저장소 전체의 `GLOSSARY.md`·`GLOSSARY-MAP.md`에 적용한다.

## 문서 배치

| 위치 | 포함할 내용 | 포함하지 않을 내용 |
| --- | --- | --- |
| `requirements/` | 문제, 목표, 범위, 제약, 우선순위, 수용 기준 | 구현 선택, 상세 형식, 절차 |
| `specs/` | 외부 동작, 업무 관계(소속·개수), 상태 전이, 오류, 통신 절차, 화면 흐름·상태·입력 검증, 텍스트 와이어프레임 | 선택의 역사, 긴 배경, 모듈 내부 구조, 코드 타입·파일, 시각 디자인 원본의 복제 |
| `design/` | `DESIGN.md`(토큰·시각 원칙·참고 자료), 스펙별 HTML 시안(`mockups/`) | 화면 동작·상태·수용 테스트, 코드에 스타일을 적용하는 규칙 |
| `contracts/` | 만드는 쪽과 사용하는 쪽, 교환 형식, 버전, 호환성 | 제품 배경, 전체 상태 전이, 운영 절차 |
| `architectures/` | 코드 지도(코드 위치·진입점·핵심 흐름), 도메인 모델(용어와 코드 타입·연결·조건 위치의 대응), 모듈 설계(내부 구조·데이터 모델·처리 순서·초기화 시점), 의존 관계, 권한 확인 경계 | 선택의 역사, 교환 형식, 외부 동작, 용어와 업무 관계의 정의, 화면 배치, 절차 |
| `decisions/` | 배경, 결정, 대안, 결과, 재검토 조건 | 요구사항 복제, 사용 안내 |
| `explainers/` | 개념, 원리, 아키텍처 문서를 따라 코드를 읽는 방법, 선택의 장단점 | 필수·금지 사항, 구조의 기준 정의, 작업 절차 |
| `conventions/` | 이름 짓기, 소스·테스트·서식 규칙, 준수 확인 방법 | 제품 동작, 구조 결정, 운영 절차 |
| `how-to/` | 전제 조건, 단계, 검증, 복구 | 결정 근거의 반복 |
| `incidents/` | 영향, 경과, 원인·가설, 대응·복구 결과, 후속 조치, 증거 | 새 기준의 정의, 반복할 절차, 근거 없는 원인 단정 |
| `templates/` | 복제할 템플릿 원본 | 작성한 프로젝트 문서, 채택된 기준, 문서 목록 |
| `GLOSSARY.md`·`GLOSSARY-MAP.md`(루트 또는 맥락 폴더) | 용어 이름, 한두 문장 정의, 쓰지 않을 표현, 맥락 목록과 관계 | 요구사항, 동작, 구현, 코드 위치, 결정 이유, 일반 프로그래밍 개념 |

## 연결 원칙

`A → B`는 A에서 정한 내용이 B의 근거라는 뜻이다. B는 A의 결정을 바꾸지 않는다. B가 문서이면 A를 링크하고, 코드이면 A와 대조해 확인한다.

```text
PRD → 스펙 → 계약
PRD / 스펙 → ADR
스펙 / DESIGN.md → HTML 시안
PRD / 스펙 / 계약 / ADR → 아키텍처 문서(코드 지도·도메인 모델·모듈 설계)
용어집 / 스펙 → 도메인 모델
ADR / 아키텍처 문서 → 컨벤션
DESIGN.md → 프런트엔드 컨벤션
스펙 / 계약 / 아키텍처 문서 / 컨벤션 / 채택된 HTML 시안 → 코드
모든 기준 문서 → 해설 / how-to
당시의 기준 문서·버전 → 사고 기록
```

- 같은 사실의 기준 문서는 하나만 둔다. 다른 문서는 복제하지 않고 링크한다. 예: 용어의 정의는 용어집, 시각 값은 `DESIGN.md`.
- 스펙 시나리오는 [검증 기록](#검증-기록)의 테스트 태그로 코드에 연결한다.
- HTML 시안은 예외로 스펙을 링크하지 않는다. 시안은 화면 ID와 상태 이름을 표시하고, 스펙 헤더 표의 `HTML 시안` 항목이 시안을 링크한다. 시안과 스펙이 다르면 스펙을 따른다([HTML 시안](design/AGENTS.md#html-시안)).
- 화면을 새로 만들거나 구성을 바꾸는 코드는 채택된 HTML 시안이 있어야 시작한다. 시각 구성은 시안, 동작과 상태는 스펙이 근거다. 구현한 화면은 시안과 같은 화면 폭·상태로 대조한다(`frontend-workflow` 스킬의 F5).
- 템플릿의 적용·갱신·도구 연결 안내는 템플릿 저장소의 루트 README에 두고, 프로젝트에 복사할 `docs/`에는 넣지 않는다.

## 문서 작성과 목록 갱신

1. 독자의 질문과 문서의 소유 범위를 정한다. 같은 질문을 다루는 문서가 있으면 그 문서를 갱신한다.
2. 새 문서는 해당 디렉터리 `AGENTS.md`의 「시작 템플릿」에서 골라 복제하고, 자리표시자를 프로젝트의 근거로 채운다([템플릿 원본 규칙](templates/AGENTS.md)). 기준 문서와 요구사항 ID를 연결한다.
3. 해당 디렉터리 `README.md` 목록에 등록한다. 템플릿과 작성 예정 문서는 등록하지 않는다.
4. [완료 점검](#완료-점검)을 한다.

문서를 나누거나 옮길 때는 내용을 복제하지 않고 이동·분리한다. 옮기거나 이름을 바꾸면 저장소 전체의 상대 링크를 고친다. 이전 주소의 안내 문서는 외부 링크를 유지할 명확한 이유가 있을 때만 남긴다.

## 기준 문서 적용과 충돌 처리

문서의 존재와 채택 여부를 구분한다. 코드만 수정할 때도 적용한다. 상태 이름은 문서 유형별 이름을 그대로 쓴다.

| 상태·표시 | 구현할 때의 판단 |
| --- | --- |
| `Draft` · `Proposed` | 사용자 지시나 채택된 ADR에서 확정 근거를 찾는다. 있으면 상태·채택 범위를 갱신한 뒤 적용한다. 이미 받은 결정을 다시 묻지 않는다. |
| `Active` · `Accepted` | 정한 대상·버전·범위 안에서 기준이다. 영향을 주는 미결정 사항은 따로 확인한다. |
| `Deprecated` | 신규 적용을 피하고, 기존 지원 범위와 대체 문서를 확인한다. |
| `Retired` · `Rejected` · `Superseded` | 구현의 근거가 아니다. 이력 확인에만 쓰고 현재 기준을 찾는다. |
| `Verified` | 구현·실행 결과와 대조했다는 표시다. 채택 여부나 테스트 통과를 뜻하지 않는다. |
| `Current` · `Target` · `Transitional` · `Historical` | 구조의 시점이다. 채택 여부는 문서 상태로 따로 확인한다. |

- 적용 상태가 없는 기준 문서는 첫 부분에 적용 범위와 채택 근거를 쓴다.
- 기준 문서가 없으면 요청·기존 문서·설정에서 확정된 내용을 찾아 기록한다. 기존 구현은 현재 동작의 증거일 뿐, 목표 요구사항의 채택 근거가 아니다.

문서와 코드, 또는 문서끼리 다르면 적용 대상·버전·채택 상태·ADR을 확인한다. 내용별 기준은 [문서 배치](#문서-배치)를 따른다. 최근 수정 시각만으로 기준을 고르지 않는다.

```text
별도 변경 결정이 없다             → 구현을 채택된 기준에 맞춘다.
사용자 지시에 기준 변경이 있다     → 근거를 기록하고 진행한다.
새 결정이 필요하거나 근거가 없다   → 내용·선택지·영향을 사용자에게 제시하고 영향받는 작업만 보류한다.
                                  결정 후 문서와 구현을 함께 갱신한다.
```

## 검증 기록

```text
시나리오 ID(스펙 수용 테스트 표) + 테스트 메타 정보 + 실행 결과
  → 보고 도구·명령
  → 시나리오별 커버리지·결과 보고서
     `미연결`: 테스트가 없는 시나리오
     `오류`:   없는 시나리오를 가리키는 메타 정보
     통과·실패: 시나리오별 테스트 결과
```

- 테스트 메타 정보(어노테이션·태그)에 `<specs/ 기준 상대 경로>:<시나리오 ID>`를 넣어야 한다. 경로는 확장자를 포함하고 하위 폴더는 `/`로 구분한다. 예: `login-screen.md:SCN-003`, `auth/login-screen.md:SCN-003`. 메타 정보가 없는 프레임워크는 테스트 이름에 넣을 수 있다. 테스트와 시나리오는 여러 개씩 연결할 수 있다.
- 스펙의 수용 테스트 표에는 시나리오와 기대 결과만 정의한다. 테스트 위치·결과·실행 기록은 쓰지 않는다.
- 보고서는 메타 정보에서 도구로 생성해야 한다. 메타 정보 문법, 보고 명령, 보고서·CI 결과 위치는 테스트 컨벤션에 정의해야 한다. 로컬 보고서는 [부수 파일 위치](../AGENTS.md#부수-파일-위치)에 따라 `.work/reports/`에 둔다.
- 계약 테스트는 계약 문서에서, 문서·컨벤션·운영 검증은 검증 how-to나 해당 문서에서 관리하고 다른 문서는 링크한다.
- 실행 기록에는 대상 버전·변경 범위, 환경, 명령 또는 확인 방법, 실제 결과를 적어야 한다. 이를 담은 CI 실행 링크로 대신할 수 있다. CI가 없으면 로컬 실행 기록과 커밋을 연결한다.
- 커밋이나 테스트 파일 링크만으로 통과를 표시해서는 안 된다.
- 작업 트리에서 검증했으면 대상 커밋과 미커밋 범위를 구분한다. 결과는 `통과`·`실패`·`미실행`으로 쓰고, 미실행은 이유와 영향을 적는다.
- 구조 대조의 `Verified`에는 대조한 커밋 또는 작업 트리 범위와 확인 기록을 연결한다.

## 작성 원칙

- 글쓰기는 루트의 [쉬운 기술 글쓰기 규칙](../AGENTS.md#쉬운-기술-글쓰기)을 따른다.
- 수용 기준과 필수·금지 동작은 관찰하거나 테스트할 수 있게 쓴다.
- 미확정 값을 임의의 기본값으로 채우지 않고 책임자와 확정 위치를 적는다.
- 현재 상태 문서는 갱신할 때 과거 상태를 덧붙이지 않고 대체되거나 중복된 내용을 정리한다. 과거 내용은 근거·제약·추적에 필요할 때만 남기고, 결정·사고·검증 기록은 해당 유형의 문서에 두고 링크한다.
- 긴 배경 지식은 `explainers/`로 분리한다.
- 해설·코드 지도·도메인 모델·모듈 설계는 템플릿의 절 구성 안에서 `explain` 스킬의 설명 순서와 쉬운 언어를 따른다. 코드 위치는 실제 파일·심볼로 연결하고 사실과 추정을 구분한다.

## 용어집

용어집은 이 프로젝트의 유비쿼터스 언어(업무 담당자·기획자·개발자가 같은 뜻으로 쓰는 업무 언어)를 기록한다.

| 질문 | 소유 문서 |
| --- | --- |
| 용어가 무엇을 뜻하는가? | 용어집 |
| 개념 사이의 업무 관계는 무엇인가? | 스펙 |
| 용어가 어느 코드 타입·파일에 있고 어떻게 연결되는가? | [도메인 모델](architectures/AGENTS.md#도메인-모델) |

용어집은 `docs/` 밖에, 맥락(DDD의 바운디드 컨텍스트)마다 하나 둔다. 같은 단어의 뜻이 달라지면(예: 주문의 "취소"와 결제의 "취소") 맥락을 나누는 근거가 될 수 있다.

```text
<저장소 루트>/
├── GLOSSARY.md               맥락이 하나일 때의 용어집 또는 공통 용어집
├── GLOSSARY-MAP.md           맥락이 둘 이상이면 필수. 맥락 목록과 관계
└── <맥락 폴더>/GLOSSARY.md    독립된 맥락의 용어집
```

### 용어집 위치

의존성과 빌드 결과 폴더를 빼고 `GLOSSARY.md`를 찾은 뒤 아래 표를 따른다. 용어집끼리 우선순위는 없다.

| 저장소 상태 | 할 일 |
| --- | --- |
| 루트에 `GLOSSARY-MAP.md`가 있다. | 맵에서 변경 대상이 속한 맥락의 용어집을 읽는다. 맥락이 불분명하면 사용자에게 묻는다. 맵에 없는 `GLOSSARY.md`는 누락으로 보고한다. |
| 맵 없이 루트 `GLOSSARY.md`만 있다. | 맥락이 하나다. 루트 용어집을 읽는다. |
| 맵 없이 하위 폴더에 `GLOSSARY.md`가 있다. | 대상 폴더와 루트의 용어집을 읽고 맵 누락을 알린다. 정의가 충돌하면 채택 근거를 확인한다. |
| 용어집이 없다. | 처음 용어를 확정할 때 루트 `GLOSSARY.md`를 만든다. 빈 파일을 미리 만들지 않는다. |

하위 용어집은 독립된 맥락에만 만든다. 공통 용어집도 맵에 등록한다. 발견한 맵 누락은 같은 변경에서 보완한다.

### 용어집 형식

`GLOSSARY.md`는 다음 형식으로 쓴다. 도메인 모델 문서가 아직 없으면 "코드와의 대응" 줄을 지운다.

```md
# {{맥락 이름}} 용어집

{{이 맥락이 무엇이고 왜 따로 있는지 한두 문장으로 쓴다.}}

코드와의 대응: [{{맥락 이름}} 도메인 모델]({{도메인 모델 문서 경로}})

## 용어

**{{용어}}({{코드에서 쓰는 영어 이름}})**:
{{무엇인지 한두 문장으로 정의한다.}}
_Avoid_: {{같은 개념을 가리키지만 쓰지 않을 표현}}
```

`GLOSSARY-MAP.md`는 다음 형식으로 쓴다. 맥락 링크는 맵 파일에서 각 용어집까지의 상대 경로다.

```md
# 용어집 맵

## 맥락

- [{{맥락 이름}}](./{{폴더 경로}}/GLOSSARY.md): {{이 맥락이 맡는 일}}

## 관계
```

### 용어집 유지보수

- 용어는 코드보다 먼저, PRD·스펙·ADR을 쓰는 시점에 그 자리에서 등록하고 고친다. 작업 끝에 몰아서 고치지 않는다.
- PRD·스펙·ADR·코드는 맥락의 정식 용어를 써야 한다. 현장 표현과 동의어는 `_Avoid_`에 남긴다.
- 요청·문서·코드의 용어가 다르면 차이와 근거를 밝힌다. 근거가 없으면 사용자에게 확인한다.
- 한 단어가 여러 뜻이면 뜻마다 용어를 제안한다. 예: "계정"이 주문하는 고객인지 로그인한 사용자인지 나눈다.
- 이름이나 뜻을 바꾸면 관련 문서를 고친다. 코드 식별자의 변경 범위는 사용자 지시와 호환성으로 판단하고, 남은 차이는 적용 범위나 미결정 사항에 적는다.
- 맥락 용어집을 추가·이동·삭제하면 같은 변경에서 `GLOSSARY-MAP.md`를 고친다.
- 용어를 추가하거나 뜻을 바꾸면 루트 지침의 [도메인 모델과 용어](../AGENTS.md#도메인-모델과-용어) 표를 보고한다.
- 뜻이 채택된 기준 문서와 충돌하면 [기준 문서 적용과 충돌 처리](#기준-문서-적용과-충돌-처리)를 따른다.

## 완료 점검

1. 문서의 위치와 내용이 [문서 배치](#문서-배치)와 맞는가?
2. 요구사항 ID와 내부 파일·제목 링크가 유효한가?
3. 용어가 [용어집](#용어집)과 맞고, 작업 중 확정한 용어를 용어집에 반영했는가?
4. 상태, 적용 범위, 미결정 사항이 실제 채택 여부와 맞는가?
5. 시나리오 메타 정보, 커버리지·결과 보고서, 실행 증거를 [검증 기록](#검증-기록)대로 연결했는가?
6. 실제 문서가 템플릿이나 자리표시자 대신 채택된 기준을 연결하는가?
7. 소스 예제와 이름이 `Active` 컨벤션을 따르는가?
8. 코드 지도·모듈 설계·도메인 모델의 경로와 심볼이 실제 코드와 맞는가? 도메인 모델이 용어집·스펙과 맞고, `(계획)`이 구현하지 않은 이름에만 남았는가?
