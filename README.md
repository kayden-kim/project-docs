# 프로젝트 문서 템플릿

에이전트와 사람이 같은 요구사항·설계에 따라 구현하도록 돕는 템플릿이다. 문서 양식, 작성 지침, 작업 절차와 스킬을 제공한다. 코드 지도·도메인 모델·모듈 설계로 구현의 구조와 흐름을 설명한다.

문서 유형과 소유 범위는 [문서 안내](docs/README.md)를, 작업 단계와 순서는 [작업 지침](AGENTS.md#작업-단계-선택)을 따른다. 프레임워크·라이브러리·실행 명령은 각 프로젝트의 요구사항과 환경에 맞게 정한다.

## 시작 경로 선택

| 상황 | 시작할 곳 |
| --- | --- |
| 새 프로젝트를 이 템플릿으로 시작한다. | [새 프로젝트 시작](#새-프로젝트-시작) |
| 기존 프로젝트에 처음 적용하거나 변경된 템플릿을 반영한다. | [기존 프로젝트에 템플릿 변경 반영](#기존-프로젝트에-템플릿-변경-반영) |
| 템플릿을 적용했고 첫 기능을 진행한다. | [적용 후 첫 기능](#적용-후-첫-기능) |
| 프런트엔드 디자인과 컴포넌트를 준비한다. | [프런트엔드 준비](#프런트엔드-준비) |
| 템플릿 구조가 작업 상황마다 필요한 문서로 안내하는지 평가한다. | [템플릿 구조 검증](#템플릿-구조-검증) |

이 README는 템플릿 사용 안내다. 원본 관리와 복제는 [템플릿 규칙](docs/templates/AGENTS.md)을 따른다. 문서 목록에는 작성한 프로젝트 문서만 등록한다.

## 새 프로젝트 시작

1. 템플릿 원본을 확보한다.
2. 대상 저장소의 기존 문서·규칙과 로컬 변경을 확인한다.
3. 아래 범위의 파일을 대상 저장소로 복사한다. `docs/`는 전체 하위 디렉터리 구조를 그대로 이식한다. 기존 파일은 [갱신 절차](#기존-프로젝트에-템플릿-변경-반영)에 따라 병합한다.
4. 각 `docs/` 폴더의 `README.md` 문서 인덱스를 실제 작성 문서에 맞춘다. 문서가 없으면 빈 목록을 유지하고, 템플릿·작성 예정 문서는 등록하지 않는다.
5. [스킬 설치](#스킬-설치), [에이전트 연결](#에이전트-연결), [적용 결과 확인](#적용-결과-확인)을 진행한다.
6. [적용 후 첫 기능](#적용-후-첫-기능)에 따라 첫 기능을 진행한다.

| 복사 범위 | 대상에서의 처리 |
| --- | --- |
| `docs/` | 전체 하위 디렉터리 구조, 작성 지침과 시작 양식을 그대로 복사한다. 각 폴더의 `README.md` 인덱스는 실제 작성 문서에 맞춘다. `design/mockups/`는 별도 README 없이 `docs/design/README.md`에서 등록한다. |
| 루트 `AGENTS.md` | 기존 규칙을 보존하며 병합한다. 프로젝트별 지침 자리표시자는 [프로젝트 초기 설정](AGENTS.md#1-프로젝트-초기-설정) 단계에서 채운다. |
| `.agents/skills/` | 대상 저장소에 복사하지 않는다. [스킬 설치](#스킬-설치)에 따라 사용자 디렉터리에 설치한다. |
| `.gitignore`의 `/.work/` 항목 | [부수 파일 위치](AGENTS.md#부수-파일-위치)의 `.work/`가 Git에서 제외되도록 병합한다. |

이 README, `.git`, `.agents/`, `.claude` 링크와 원본의 로컬 설정은 복사하지 않는다. 제품 README에는 제품 설명과 실행 방법을 쓴다. 시작 양식을 일부 빼면 그 양식을 가리키는 지침과 링크도 고친다.

`{{...}}`는 프로젝트 정보로 채울 자리표시자다. 사용하지 않는 예시와 선택 항목은 제거한다.

## 기존 프로젝트에 템플릿 변경 반영

기존 프로젝트의 문서·규칙·스킬을 보존하면서 필요한 변경을 병합한다. 최초 적용도 기존 파일이 있다면 이 방식을 사용한다.

1. 이전 원본이 있으면 새 원본·이전 원본·현재 파일을 비교한다. 이전 원본이 없으면 새 원본과 현재 파일을 비교한다.
2. 변경 항목을 반영·일부 반영·제외로 분류한다.
3. 아래 파일별 기준에 따라 필요한 변경을 병합한다.
4. [적용 결과 확인](#적용-결과-확인)과 영향받은 프로젝트 검증을 실행한다.
5. 영향받은 문서·지침·링크만 갱신한다. 별도의 템플릿 반영 기록은 작성하지 않는다.

| 구분 | 갱신할 때의 판단 |
| --- | --- |
| 변경하지 않은 시작 양식 | 이전 원본과 같았는지 확인한 뒤 새 원본으로 갱신한다. |
| 프로젝트에서 수정한 시작 양식 | 이전 원본·새 원본·프로젝트 수정 내용을 비교해 필요한 항목을 병합한다. |
| 작성된 프로젝트 문서 | 필요한 새 항목만 반영한다. 확정된 요구사항·ID·상태·설계·테스트 증거를 빈 템플릿으로 바꾸지 않는다. |
| `docs/` 구조·폴더별 `README.md` | 템플릿의 모든 하위 디렉터리를 반영하고 기존 프로젝트 전용 폴더와 문서는 보존한다. 각 인덱스를 실제 작성 문서에 맞추고, 문서가 없으면 비워 둔다. 템플릿·작성 예정 문서는 등록하지 않는다. |
| 작업 지침 | 프로젝트 고유 규칙과 링크를 보존하면서 갱신한다. 루트 `AGENTS.md`의 프로젝트별 지침 자리표시자는 현재 프로젝트의 문서·설정에 맞게 채우고, 예시 항목을 고정 목록으로 만들지 않는다. |
| 저장소의 템플릿 스킬 사본 | 사본에 프로젝트에서 고친 내용이 있는지 확인한다. 프로젝트 규칙은 프로젝트 문서로 옮기고 사본은 제거한다. 스킬은 [스킬 설치](#스킬-설치)에 따라 사용자 디렉터리에서 갱신한다. 템플릿에 없는 프로젝트 전용 스킬은 보존한다. |
| 흩어진 부수 파일 폴더 | 위치와 크기를 목록으로 보고한다. 지우거나 `.work/`로 옮기기 전에 사용자에게 확인한다. |
| 원본에서 삭제·이동한 파일 | 프로젝트의 사용 여부와 참조를 확인하고 필요한 대체 경로를 연결한다. |

출처가 불분명한 내용은 보존한다. 보류하거나 제외한 변경은 현재 프로젝트에 필요한 지침과 링크가 유지되는지 확인한다.

## 적용 후 첫 기능

적용한 뒤에는 대상 저장소의 루트 `AGENTS.md`가 작업 단계를 안내한다. 사용자가 완료할 첫 기능 하나를 정한다. 그 기능을 [프로젝트 초기 설정](AGENTS.md#1-프로젝트-초기-설정), [구현 전 계획](AGENTS.md#2-구현-전-계획), [구현](AGENTS.md#3-구현) 순서로 진행한다. 첫 기능을 검증한 뒤 다음 기능으로 넓힌다.

에이전트에게 단계별로 요청할 수 있다.

```text
이 템플릿을 적용한 프로젝트의 초기 설정을 진행해 줘.
AGENTS.md 「1. 프로젝트 초기 설정」에 따라 기존 문서와 설정을 확인해 줘.
실행·검증 명령은 실제로 실행해 결과를 확인해 줘.
```

```text
첫 기능의 구현 전 계획을 세워 줘.
AGENTS.md 「2. 구현 전 계획」에 따라 PRD·용어집·스펙·도메인 모델을 작성해 줘.
기존에 확정된 선택은 재사용하고 미결정 사항은 영향 범위와 함께 제시해 줘.
```

```text
채택된 기준에 따라 첫 기능을 구현해 줘.
시나리오 태그가 있는 테스트를 실행하고 커버리지·결과 보고서를 연결해 줘.
미실행 검증과 남은 결정을 구분해 줘.
```

## 프런트엔드 준비

[`frontend-workflow` 스킬](.agents/skills/frontend-workflow/SKILL.md)에 따라 F1~F5 순서로 진행한다. 동작 문서 완료, 참고 디자인 수집, DESIGN.md 확정(`Accepted`), 화면별 HTML 시안, 구현과 대조 순서다. 순서별 절차는 [스킬의 참고 문서](.agents/skills/frontend-workflow/references/frontend-workflow.md#4-디자인-탐색과-대표-화면)에서 관리한다.

| 산출물 | 역할 |
| --- | --- |
| 디자인 시스템 | 토큰, 시각 원칙, 참고 자료의 채택 요소, 컴포넌트 변형·상태와 예외 |
| 프런트엔드 컨벤션 | 토큰 원본·생성 관계, 스타일 적용·재사용, 미리보기와 검증 규칙 |
| 화면 스펙 | 화면 동작과 수용 테스트. 단순 화면은 관련 스펙의 화면 절 사용 |
| HTML 시안 | 화면을 정한 스펙(화면 스펙 또는 스펙의 화면 절)마다 `docs/design/mockups/`에 두는 시각 확인용 파일. 모든 화면 ID와 상태를 보여 주며 동작 기준은 아니다. |
| 실제 컴포넌트 미리보기 | 앱의 컴포넌트와 공통 스타일로 필요한 상태를 재현하는 실행 예시 |

미리보기 방식과 시안·구현 검증의 구분은 프로젝트의 프런트엔드 컨벤션을 따른다. 기존 미리보기 환경이 있으면 재사용한다.

## 스킬 설치

템플릿 스킬은 대상 저장소에 복사하지 않고 사용자 디렉터리에 한 벌만 설치한다. 저장소마다 사본을 두면 템플릿을 갱신할 때 사본끼리 내용이 달라진다. 스킬은 프로젝트 문서를 저장소 루트 기준 경로로 찾으므로 모든 프로젝트에서 같은 본문을 쓸 수 있다. 프로젝트마다 다른 규칙은 스킬이 아니라 프로젝트 문서에 둔다.

| 도구 | 사용자 스킬 위치 |
| --- | --- |
| Codex | `~/.agents/skills/` |
| Claude Code | `~/.claude/skills/` |

Windows에서 `~`는 `%USERPROFILE%`이다.

1. 템플릿 원본의 `.agents/skills/<스킬 이름>/` 디렉터리를 `~/.agents/skills/<스킬 이름>/`에 복사한다.
2. 같은 이름의 스킬이 이미 있으면 차이를 확인한다. 사용자가 고친 내용은 보존하면서 병합한다.
3. Claude Code를 쓰면 아래 표에서 조건에 맞는 명령 하나로 `~/.claude/skills`를 연결한다.
4. 새 세션에서 도구가 템플릿 스킬을 목록에 표시하는지 확인한다.

| 조건 | Windows 명령 프롬프트 | macOS·Linux |
| --- | --- | --- |
| `~/.claude/skills`가 없음 | `mklink /J "%USERPROFILE%\.claude\skills" "%USERPROFILE%\.agents\skills"` | `ln -s ~/.agents/skills ~/.claude/skills` |
| `~/.claude/skills`가 이미 있음 | 스킬마다 연결한다. 예: `mklink /J "%USERPROFILE%\.claude\skills\explain" "%USERPROFILE%\.agents\skills\explain"` | 스킬마다 연결한다. 예: `ln -s ~/.agents/skills/explain ~/.claude/skills/explain` |

기존 `~/.claude/skills`를 지우고 링크로 바꾸지 않는다. 같은 이름의 스킬 디렉터리가 이미 있으면 링크 대신 파일별로 병합한다.

## 에이전트 연결

작업 규칙은 대상 저장소의 `AGENTS.md`와 하위 지침에 둔다. 도구별 연결 파일에 본문을 복제하지 않는다. 적용 후 실제 도구가 프로젝트의 지침과 필요한 스킬을 읽는지 확인한다.

Claude Code를 쓰면 기존 `CLAUDE.md`의 규칙은 보존한다. 공식 안내에 따라 `CLAUDE.md`에서 `AGENTS.md`를 참조한다.

## 적용 결과 확인

프로젝트의 문서와 규칙을 바꾸기 전에 기존 변경을 보존한다. 적용 뒤에는 아래 항목을 확인한다. 검사 명령은 대상 프로젝트의 설정과 CI에서 찾는다.

| 확인 대상 | 성공 조건 |
| --- | --- |
| 문서 목록과 링크 | 템플릿의 모든 `docs/` 하위 폴더와 기존 프로젝트 전용 폴더가 유지되고, 각 폴더의 `README.md` 인덱스가 실제 작성 문서와 일치하며 로컬 파일·제목 링크가 유효하다. `design/mockups/`의 시안은 `docs/design/README.md`에 등록되어 있다. |
| 기준 문서 | 기존 요구사항·ID·상태·설계·테스트 증거가 보존되고 새 항목의 근거를 찾을 수 있다. |
| 작성 지침 | 시작 양식은 각 `AGENTS.md`에서 찾을 수 있다. 실제 문서는 작성된 기준 문서를 연결한다. |
| 스킬과 도구 연결 | 대상 저장소에 템플릿 스킬 사본이 없고, 사용자 디렉터리의 스킬이 템플릿 원본과 같거나 차이를 설명할 수 있다. 실제 도구가 지침과 스킬을 읽는다. |
| 부수 파일 위치 | 대상 `.gitignore`가 `/.work/`를 제외한다. 흩어진 기존 부수 파일 폴더를 보고했다. |
| 영향받은 구현 | 변경된 기준과 구현이 일치하고 필요한 테스트·검증이 통과했다. |

파일 복사와 정적 확인만으로 실제 도구 연결이나 앱 실행까지 검증했다고 표시하지 않는다. 실행하지 못한 검증은 이유와 영향 범위를 남긴다. 검증이 실패하면 이번에 바꾼 범위를 변경 전 상태와 대조하고 필요한 파일만 되돌린다. 기존 사용자 변경은 함께 지우지 않는다.

## 템플릿 구조 검증

템플릿 구조 검증은 작업 상황마다 에이전트가 루트 `AGENTS.md`에서 출발해 필요한 규칙과 시작 템플릿을 찾는지 확인하는 일이다. 지침이나 템플릿의 구조를 바꾼 뒤, 또는 템플릿을 프로젝트에 맞게 고친 뒤에 진행한다. 링크 검사는 경로가 살아 있는지만 확인한다. 에이전트가 맞는 단계와 규칙을 고르는지는 이 시뮬레이션으로 확인한다.

요청할 때 아래 조건을 지정한다.

| 조건 | 이유 |
| --- | --- |
| 상황마다 새 에이전트를 쓴다. 하위 에이전트를 쓸 수 없으면 상황마다 새 세션을 연다. | 앞 상황에서 읽은 내용이 다음 판단에 섞이지 않는다. |
| 루트 `AGENTS.md`부터 읽고, 읽은 문서가 링크·경로·스킬 이름으로 가리키는 파일만 연다. 검색·목록 조회·사전 지식은 쓰지 않는다. | 문서의 안내만으로 길을 찾는지 확인한다. 검색을 허용하면 빠진 안내가 드러나지 않는다. |
| 상황마다 프로젝트 가정을 적는다. 예: 작업 안내를 채웠는지, 코드가 있는지, 어떤 문서가 있는지. | 템플릿 원본은 문서 목록이 비어 있고 자리표시자가 남아 있다. 가정이 없으면 이를 결함으로 보고한다. |
| 읽기만 하고 문서를 고치지 않는다. | 평가와 수정을 나눈다. |
| 보고된 지적은 현재 문서와 대조해 확인한 것만 남긴다. | 에이전트가 이미 있는 규칙을 놓치거나 가정과 다르게 판단할 수 있다. |

전체 평가 요청 예:

```text
현재 템플릿 구조가 작업 상황마다 필요한 문서로 안내하는지 시뮬레이션으로 검증해 줘.
상황마다 읽기 전용 하위 에이전트를 하나씩 써 줘. 각 에이전트는 루트 AGENTS.md부터 읽고, 읽은 문서가 링크·경로·스킬 이름으로 가리키는 파일만 열게 해 줘. 검색·목록 조회·사전 지식은 쓰지 않게 해 줘.
상황과 프로젝트 가정은 아래와 같아.
1. 기존 코드 저장소의 초기 설정: TypeScript 백엔드 코드, 린터·포매터 설정, 테스트가 있다. 템플릿을 막 적용했다.
2. 코드 없는 새 프로젝트: 빈 저장소에 템플릿을 적용했다. 첫 기능은 할 일 추가 화면이다.
3. 새 업무 개념의 구현 전 계획: 초기 설정이 끝났다. 코드에 `Order`가 있고 도메인 모델 문서는 없다. 요청은 주문 쿠폰 할인이다.
4. 단순 화면 기능: 초기 설정이 끝났다. DESIGN.md가 없다. 요청은 할 일 입력란(입력 1개, 화면 이동 없음)이다.
5. 결함 수정: 초기 설정이 끝났다. 채택된 스펙에 결제 전 취소 불변식 시나리오가 있다. 요청은 결제 후에도 주문이 취소되는 버그 수정이다.
6. 문서만 작성: 초기 설정과 구현이 끝났다. 작업 안내의 도메인 모델 칸은 `없음`이다. 요청은 결제 흐름 해설이다.
템플릿의 빈 목록과 자리표시자는 위 가정에 따라 판단하게 해 줘.
각 에이전트는 읽은 순서, 작업 계획, 막힌 곳(심각도·위치·최소 수정), 한 줄 판정을 보고하게 해 줘.
지적은 현재 문서와 대조해 확인한 것만 남겨 줘. 문서는 고치지 말고 결과만 보고해 줘.
```

수정 후 재검증 요청 예:

```text
방금 고친 문서에 영향받는 상황만 이전 평가와 같은 탐색 조건과 프로젝트 가정으로 다시 시뮬레이션해 줘.
이전에 막혔던 곳마다 해결됨·부분·미해결로 판정하고 파일과 줄 번호를 근거로 붙여 줘.
새로 나온 문제는 이전 문제와 나눠서 보고해 줘. 문서는 고치지 말고 결과만 보고해 줘.
```

한 상황만 확인하는 요청 예:

```text
"결제가 끝난 주문도 취소되는 버그를 고쳐 줘"라는 요청을 받은 에이전트가 필요한 규칙과 템플릿을 찾는지 시뮬레이션해 줘.
가정: 초기 설정이 끝났고, 채택된 스펙에 결제 전 취소 불변식 시나리오가 있다.
루트 AGENTS.md부터 읽고 문서가 가리키는 파일만 열게 해 줘. 검색은 쓰지 않게 해 줘.
문서는 고치지 말고 결과만 보고해 줘.
```
