# 프로젝트 문서 템플릿

에이전트와 사람이 같은 요구사항·설계에 따라 구현하도록 돕는 템플릿이다. 문서 양식, 작성 지침, 작업 절차와 스킬을 제공한다. 코드 지도와 모듈 설계로 구현의 구조와 흐름을 설명한다.

문서 유형과 소유 범위는 [문서 안내](docs/README.md)를, 실제 변경의 순서는 [작업 지침](AGENTS.md#작업-순서와-필수-참조)을 따른다. 프레임워크·라이브러리·실행 명령은 각 프로젝트의 요구사항과 환경에 맞게 정한다.

## 시작 경로 선택

| 상황 | 시작할 곳 |
| --- | --- |
| 새 프로젝트를 이 템플릿으로 시작한다. | [새 프로젝트 시작](#새-프로젝트-시작) |
| 기존 프로젝트에 처음 적용하거나 변경된 템플릿을 반영한다. | [기존 프로젝트에 템플릿 변경 반영](#기존-프로젝트에-템플릿-변경-반영) |
| 문서를 복사했고 초기 구현 설정을 준비한다. | [초기 구현을 위한 준비 문서](#초기-구현을-위한-준비-문서) |
| 프런트엔드 디자인과 컴포넌트를 준비한다. | [프런트엔드 준비](#프런트엔드-준비) |

이 README는 템플릿 사용 안내다. 원본 관리와 복제는 [템플릿 규칙](docs/templates/AGENTS.md)을 따른다. 문서 목록에는 작성한 프로젝트 문서만 등록한다.

## 새 프로젝트 시작

1. 템플릿 원본을 확보한다.
2. 대상 저장소의 기존 문서·규칙·스킬과 로컬 변경을 확인한다.
3. 아래 범위의 파일을 대상 저장소로 복사한다. `docs/`는 전체 하위 디렉터리 구조를 그대로 이식한다. 기존 파일은 [갱신 절차](#기존-프로젝트에-템플릿-변경-반영)에 따라 병합한다.
4. 루트 `AGENTS.md`의 프로젝트별 지침 자리표시자를 대상에서 확인한 규칙과 기준 문서 링크로 채운다.
5. 각 디렉터리의 `AGENTS.md`를 읽고 첫 구현에 필요한 문서를 작성한다.
6. 각 `docs/` 폴더의 `README.md` 문서 인덱스를 실제 작성 문서에 맞춘다. 문서가 없으면 빈 목록을 유지하고, 템플릿·작성 예정 문서는 등록하지 않는다.
7. [프로젝트 작업 안내](docs/README.md#프로젝트-작업-안내)에 실제 기준 문서와 실행·검증 절차를 연결한다.
8. [에이전트 연결](#에이전트-연결)과 [적용 결과 확인](#적용-결과-확인)을 진행한다.
9. [초기 구현 워크플로우](#초기-구현-워크플로우)에 따라 첫 기능을 구현한다.

| 복사 범위 | 대상에서의 처리 |
| --- | --- |
| `docs/` | 전체 하위 디렉터리 구조, 작성 지침과 시작 양식을 그대로 복사한다. 각 폴더의 `README.md` 인덱스는 실제 작성 문서에 맞춘다. `specs/mockups/`는 별도 README 없이 `docs/specs/README.md`에서 등록한다. |
| 루트 `AGENTS.md` | 기존 규칙을 보존하고 프로젝트별 지침 자리표시자를 대상에서 확인한 내용으로 채운다. |
| `.agents/skills/` | 필요한 스킬을 복사한다. 제외한 스킬의 참조도 함께 맞춘다. |
| `.gitignore`의 Claude 연결 항목 | [연결 방식](#에이전트-연결)에 필요한 항목만 병합한다. |

이 README, `.git`, 원본의 로컬 설정과 `.claude` 링크는 복사하지 않는다. 제품 README에는 제품 설명과 실행 방법을 쓴다. 양식이나 스킬을 제외하면 관련 지침과 링크도 맞춘다.

`{{...}}`는 프로젝트 정보로 채울 자리표시자다. 사용하지 않는 예시와 선택 항목은 제거한다.

코드가 없는 프로젝트의 코드 지도는 [아키텍처 규칙](docs/architectures/AGENTS.md)을 따른다. 구현 기준의 채택은 [문서 적용 규칙](docs/AGENTS.md#기준-문서-적용과-충돌-처리)을 따른다.

## 기존 프로젝트에 템플릿 변경 반영

기존 프로젝트의 문서·규칙·스킬을 보존하면서 필요한 변경을 병합한다. 최초 적용도 기존 파일이 있다면 이 방식을 사용한다.

1. 이전 원본이 있으면 새 원본·이전 원본·현재 파일을 비교한다. 이전 원본이 없으면 새 원본과 현재 파일을 비교한다.
2. 변경 항목을 반영·일부 반영·제외로 분류한다.
3. 아래 파일별 기준에 따라 필요한 변경을 병합한다.
4. [적용 결과 확인](#적용-결과-확인)과 영향받은 프로젝트 검증을 실행한다.
5. 영향받은 문서·지침·링크만 갱신한다. 별도의 템플릿 반영 기록은 작성하지 않는다.

| 구분 | 갱신할 때의 판단 |
| --- | --- |
| 변경하지 않은 시작 양식 | 이전 원본과 같았는지 확인한 뒤 새 원본으로 갱신한다. |
| 프로젝트에서 수정한 시작 양식 | 이전 원본·새 원본·프로젝트 수정 내용을 비교해 필요한 항목을 병합한다. |
| 작성된 프로젝트 문서 | 필요한 새 항목만 반영한다. 확정된 요구사항·ID·상태·설계·시험 증거를 빈 템플릿으로 바꾸지 않는다. |
| `docs/` 구조·폴더별 `README.md` | 템플릿의 모든 하위 디렉터리를 반영하고 기존 프로젝트 전용 폴더와 문서는 보존한다. 각 인덱스를 실제 작성 문서에 맞추고, 문서가 없으면 비워 둔다. 템플릿·작성 예정 문서는 등록하지 않는다. |
| 작업 지침·스킬 | 프로젝트 고유 규칙과 링크를 보존하면서 갱신한다. 루트 `AGENTS.md`의 프로젝트별 지침 자리표시자는 현재 프로젝트의 문서·설정에 맞게 채우고, 예시 항목을 고정 목록으로 만들지 않는다. |
| 원본에서 삭제·이동한 파일 | 프로젝트의 사용 여부와 참조를 확인하고 필요한 대체 경로를 연결한다. |

출처가 불분명한 내용은 보존한다. 보류하거나 제외한 변경은 현재 프로젝트에 필요한 지침과 링크가 유지되는지 확인한다.

## 초기 구현을 위한 준비 문서

사용자가 완료할 첫 작업 하나를 정한다. 그 작업의 구현과 검증에 필요한 문서부터 채운다.

### 첫 구현의 기본 문서

| 준비 문서 | 구현 전에 정할 내용 | 작성 규칙 |
| --- | --- | --- |
| PRD | 해결할 문제, 사용자, 첫 구현 범위와 수용 기준 | [PRD 작성 규칙](docs/requirements/AGENTS.md) |
| 코드 지도 | 구성요소의 책임, 예상 진입점과 연결 관계. 기존 코드는 실제 위치 | [아키텍처 문서 작성 규칙](docs/architectures/AGENTS.md) |
| 첫 기능의 스펙 | 입력·정상·오류·복구 결과와 수용 시험. 화면이 있으면 관련 화면 동작 | [스펙 작성 규칙](docs/specs/AGENTS.md) |
| 개발 환경 준비 how-to | 도구와 버전, 의존성 준비, 환경 변수 이름, 실행 위치와 시작 방법 | [how-to 작성 규칙](docs/how-to/AGENTS.md) |
| 검증 how-to | 변경 범위별 검사, 전체 완료 검증, 성공 조건과 증거 위치 | [how-to 작성 규칙](docs/how-to/AGENTS.md) |

파일명 예시는 `docs/how-to/dev-setup.md`와 `docs/how-to/verification.md`다. 기존 문서가 있으면 재사용한다. 환경 준비와 검증을 한 문서에서 다룰 수도 있다.

설정 전의 절차는 `Draft`로 둔다. 실제 설정을 만든 뒤 명령과 결과를 확인한다. [how-to 규칙](docs/how-to/AGENTS.md)에 따라 검증 상태와 비밀 값 처리를 기록한다.

### 변경 범위에 따라 추가할 문서

| 필요한 경우 | 준비 문서와 내용 |
| --- | --- |
| 코드 작성 규칙을 정한다. | 컨벤션에 이름 짓기·서식·시험 작성 규칙을 기록한다. [작성 규칙](docs/conventions/AGENTS.md)을 따른다. |
| 첫 모듈의 책임과 내부 구조를 정한다. | 모듈 설계에 공개 기능·데이터·처리 순서를 기록한다. [작성 규칙](docs/architectures/AGENTS.md)을 따른다. |
| 구성요소 사이의 교환 형식이 있다. | 계약에 형식과 호환성 기준을 기록한다. [작성 규칙](docs/contracts/AGENTS.md)을 따른다. |
| 업무 용어를 확정한다. | [용어집 규칙](docs/AGENTS.md#용어집)에 따라 이름과 뜻을 기록한다. |
| 중요한 대안을 선택한다. | [ADR 작성 조건](docs/decisions/AGENTS.md)을 모두 만족할 때만 결정 기록을 작성한다. |
| 화면의 공통 스타일과 구현 방식을 정한다. | [프런트엔드 준비](#프런트엔드-준비)에 따라 디자인 기준과 코드 적용 규칙을 기록한다. |
| 사고의 경과와 후속 조치를 추적한다. | 사건이 발생하면 [사고 기록](docs/incidents/README.md)을 작성한다. 초기 문서로 미리 채우지 않는다. |

작성한 문서는 목록과 [프로젝트 작업 안내](docs/README.md#프로젝트-작업-안내)에 연결한다.

## 초기 구현 워크플로우

첫 기능은 아래 순서로 시작하는 것을 권장한다. 이후 변경은 [작업 순서](AGENTS.md#작업-순서와-필수-참조)를 따른다.

| 단계 | 작업 | 다음 단계로 넘어갈 기준 |
| --- | --- | --- |
| 1. 범위와 기준 | 위 준비 문서를 작성한다. | 수용 기준과 채택 범위를 찾을 수 있다. |
| 2. 실행 환경 | 채택한 도구로 시작점과 의존성을 준비한다. | 시작 명령이 실행되고 결과를 기록했다. |
| 3. 검증 환경 | 필요한 린트·빌드·시험을 구성한다. | 명령과 성공 조건을 실제 설정으로 확인했다. |
| 4. 구현·검증 | 작업 지침에 따라 첫 기능을 구현하고 시험한다. | 필수 수용 기준을 통과했고 문서와 구현이 일치한다. |

기본 화면이 실행된 상태와 첫 기능이 검증된 상태를 구분한다. 첫 기능의 검증 후 다음 기능으로 확장한다.

에이전트에게 준비와 구현을 나누어 요청할 수 있다.

```text
이 템플릿을 적용한 프로젝트의 초기 구현을 준비해 줘.
기존 문서와 코드를 확인하고 첫 구현 범위를 정리해 줘.
필요한 기준 문서와 개발 환경·검증 절차를 작성해 줘.
기존에 확정된 선택은 재사용하고 미결정 사항은 영향 범위와 함께 제시해 줘.
```

```text
채택된 기준에 따라 첫 기능의 실행 환경과 구현을 준비해 줘.
실제 명령으로 시작과 검증을 확인하고 문서에 결과를 연결해 줘.
스펙의 수용 시험을 실행하고 미실행 검증과 남은 결정을 구분해 줘.
```

## 프런트엔드 준비

[`frontend-workflow` 스킬](.agents/skills/frontend-workflow/SKILL.md)에 따라 5단계로 진행한다. 동작 문서 완료, 참고 디자인 수집, DESIGN.md 확정(`Accepted`), 화면별 HTML 시안, 구현과 대조 순서다. 단계별 절차는 [스킬의 참고 문서](.agents/skills/frontend-workflow/references/frontend-workflow.md#4-디자인-탐색과-대표-화면)에서 관리한다.

| 산출물 | 역할 |
| --- | --- |
| 디자인 시스템 | 토큰, 시각 원칙, 참고 자료의 채택 요소, 컴포넌트 변형·상태와 예외 |
| 프런트엔드 컨벤션 | 토큰 원본·생성 관계, 스타일 적용·재사용, 미리보기와 검증 규칙 |
| 화면 스펙 | 화면 동작과 수용 시험. 단순 화면은 관련 스펙의 화면 절 사용 |
| HTML 시안 | 화면 스펙마다 `docs/specs/mockups/`에 두는 시각 확인용 파일. 모든 화면 ID와 상태를 보여 주며 동작 기준은 아니다. |
| 실제 컴포넌트 미리보기 | 앱의 컴포넌트와 공통 스타일로 필요한 상태를 재현하는 실행 예시 |

미리보기 방식과 시안·구현 검증의 구분은 프로젝트의 프런트엔드 컨벤션을 따른다. 기존 미리보기 환경이 있으면 재사용한다.

## 스킬과 에이전트 사용

| 스킬                                                             | 사용할 작업                         |
| -------------------------------------------------------------- | ------------------------------ |
| [frontend-workflow](.agents/skills/frontend-workflow/SKILL.md) | 프로젝트 기준에 따른 프런트엔드 디자인 탐색·구현·검토 |
| [artifact-design](.agents/skills/artifact-design/SKILL.md) | 글과 시각 자료를 연결하는 단일 HTML 아티팩트 설계·제작 |
| [explain](.agents/skills/explain/SKILL.md)                     | 결과의 개요부터 설계 이유와 실제 코드 흐름까지 설명  |

사용 예:

- `$frontend-workflow 설정 화면을 채택된 디자인 기준에 따라 구현해 줘.`
- `$artifact-design 코드 흐름과 시각 자료를 연결하는 HTML 해설 아티팩트를 만들어 줘.`

도구 연결은 [에이전트 연결](#에이전트-연결)을 따른다.

## 에이전트 연결

작업 규칙은 `AGENTS.md`와 관련 하위 지침에, 스킬 본문은 `.agents/skills/`에 둔다. 도구별 연결 파일에 본문을 복제하지 않는다. 적용 후 실제 도구가 프로젝트의 지침과 필요한 스킬을 읽는지 확인한다.

### Claude Code 연결

새 프로젝트에 `.claude/`가 없으면 `.claude`를 `.agents`에 연결할 수 있다. `.claude/`가 이미 있고 `skills/`는 없으면 `.claude/skills`만 연결한다. 기존 `skills/`가 있으면 그 내용을 보존하면서 파일별로 병합한다. 기존 디렉터리를 지우고 링크로 바꾸지 않는다.

실행 위치는 대상 저장소 루트다. 대상 경로가 없는 경우에만 아래 해당 명령 하나를 실행한다. Windows 예시는 명령 프롬프트(cmd), macOS·Linux 예시는 일반 shell에서 사용한다.

| 조건 | Windows 명령 프롬프트 | macOS·Linux | 대상 `.gitignore` 항목 |
| --- | --- | --- | --- |
| `.claude/`가 없음 | `mklink /J .claude .agents` | `ln -s .agents .claude` | `/.claude` |
| `.claude/`가 있고 `skills/`는 없음 | `mklink /J .claude\skills .agents\skills` | `ln -s ../.agents/skills .claude/skills` | `/.claude/skills` |

연결이 대상 프로젝트의 `.agents` 또는 `.agents/skills`를 가리키는지 확인한다. 링크는 프로젝트마다 만들고 Git에서 제외한다. 기존 Claude 설정을 계속 관리하면 링크 경로만 제외한다.

기존 `CLAUDE.md`의 규칙은 보존한다. 공식 안내에 따라 `AGENTS.md` 참조를 연결한다.

## 적용 결과 확인

프로젝트의 문서와 규칙을 바꾸기 전에 기존 변경을 보존한다. 적용 뒤에는 아래 항목을 확인한다. 검사 명령은 대상 프로젝트의 설정과 CI에서 찾는다.

| 확인 대상 | 성공 조건 |
| --- | --- |
| 문서 목록과 링크 | 템플릿의 모든 `docs/` 하위 폴더와 기존 프로젝트 전용 폴더가 유지되고, 각 폴더의 `README.md` 인덱스가 실제 작성 문서와 일치하며 로컬 파일·제목 링크가 유효하다. `specs/mockups/`의 시안은 `docs/specs/README.md`의 `HTML 시안` 열에 등록되어 있다. |
| 기준 문서 | 기존 요구사항·ID·상태·설계·시험 증거가 보존되고 새 항목의 근거를 찾을 수 있다. |
| 작성 지침 | 시작 양식은 각 `AGENTS.md`에서 찾을 수 있다. 실제 문서는 작성된 기준 문서를 연결한다. |
| 스킬과 도구 연결 | 스킬 형식·참고 경로가 유효하고 실제 도구가 지침과 스킬을 읽는다. |
| 영향받은 구현 | 변경된 기준과 구현이 일치하고 필요한 시험·검증이 통과했다. |

파일 복사와 정적 확인만으로 실제 도구 연결이나 앱 실행까지 검증했다고 표시하지 않는다. 실행하지 못한 검증은 이유와 영향 범위를 남긴다. 검증이 실패하면 이번에 바꾼 범위를 변경 전 상태와 대조하고 필요한 파일만 되돌린다. 기존 사용자 변경은 함께 지우지 않는다.
