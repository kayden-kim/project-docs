# 인터랙션 레퍼런스

## 적용 범위

[스킬의 인터랙션과 애니메이션 규칙](../SKILL.md#인터랙션과-애니메이션)을 따른다. 이 문서는 인터랙션을 고르는 순서, 패턴 목록, 모든 패턴에 적용하는 구현 계약을 정한다.

[템플릿](../assets/editorial-template.html)의 `.mechanism`은 단계 탐색·유한 재생·시나리오 전환을 묶은 예시 하나다. 새 아티팩트의 기본 형태가 아니다. 내용이 같은 질문에 답할 때만 그 구조를 가져온다. 다른 패턴을 만들 때도 상태 관리·취소·정적 모드 처리 방식은 참고할 수 있다.

## 설계 순서

인터랙션은 독자가 직접 바꿔 보며 답을 얻는 질문에 쓴다. 장면마다 아래 다섯 가지를 먼저 한 줄씩 적는다.

1. **질문**: 독자가 확인하려는 것. 예: "버퍼가 작아지면 언제부터 요청을 버리는가?"
2. **조작할 변수**: 독자가 바꾸는 값·대상·시점. 예: 버퍼 크기.
3. **시각 반응**: 조작하자마자 바뀌는 그림의 부분. 예: 대기열 길이와 버려진 요청 표시.
4. **결론 문장**: 조작한 뒤 독자가 말할 수 있는 문장. 캡션이나 상태 문구에 이 문장을 쓴다.
5. **기본 상태**: 조작하지 않아도 핵심을 읽을 수 있는 첫 화면.

시각 반응이나 결론 문장을 적을 수 없으면 정적 그림을 쓴다. 조작해도 그림이 거의 바뀌지 않거나 새로 알게 되는 것이 없으면 그 인터랙션은 장식이다.

## 패턴 고르기

아래 표는 출발점이다. 목록에 없는 방식도 설계 순서를 만족하면 쓸 수 있다. 한 장면에서 두 패턴을 섞을 수도 있다. 예를 들어 매개변수 탐색 결과를 시간축 스크럽으로 되짚어 볼 수 있다.

| 독자의 질문 | 패턴 | 독자의 조작 | 시각 반응 | 주의할 점 |
| --- | --- | --- | --- | --- |
| 값이 바뀌면 결과가 어떻게 달라지는가? | 매개변수 탐색 | 슬라이더, 숫자 입력, 스텝퍼 | 도식·그래프를 바로 다시 계산하고 임계점을 표시 | 계산 규칙과 출처를 밝힌다. 가정한 값은 가정이라고 표시한다. |
| 특정 시점에는 어떤 상태였는가? | 시간축 스크럽 | 타임라인 슬라이더, 이벤트 로그의 항목 선택 | 그 시점의 상태와 그때까지의 이벤트 | 처음부터 재생하는 것보다 원하는 시점으로 바로 가는 것이 중요할 때 쓴다. |
| 긴 과정을 읽는 동안 그림이 따라오게 하려면? | 스크롤 연동 장면(scrollytelling) | 스크롤 | 고정된 도식이 읽는 문단에 맞춰 단계와 강조를 바꿈 | 문단만 읽어도 뜻이 통해야 한다. 스크롤 위치를 강제로 옮기지 않는다. |
| 두 상태는 어디가 다른가? | 비교 스크러버·겹쳐 보기 | 경계선 끌기, 전후 전환, 차이만 보기 | 같은 좌표계에 놓인 두 상태와 바뀐 부분의 강조 | 두 상태의 축·크기·범례를 맞춘다. |
| 이 요소는 무엇과 연결되는가? | 연결 탐색 | 노드에 포커스·탭·호버 | 관련 경로만 강조하고 나머지는 흐리게 표시, 상세 설명 | 호버로만 정보를 열지 않는다. 포커스와 탭으로도 같은 정보를 연다. |
| 구조가 여러 겹으로 되어 있는가? | 레이어 토글·분해도 | 레이어 선택, 펼치기 | 선택한 층만 보이거나 층이 벌어져 내부가 드러남 | 모든 층을 켠 상태와 끈 상태 중 어느 쪽을 기본으로 할지 정한다. |
| 전체와 세부를 오가려면? | 점진적 공개·확대 | 영역 선택, 확대·축소, 접기·펼치기 | 개요의 위치를 유지한 채 세부가 열림 | 지금 보는 세부가 개요의 어디인지 표시한다. |
| 배치나 순서를 바꾸면 어떻게 되는가? | 직접 조작 | 끌어 놓기, 순서 바꾸기 | 정한 규칙에 따라 결과를 다시 계산 | 키보드로도 같은 조작을 할 수 있게 한다. |
| 이벤트가 들어오면 시스템은 어떻게 반응하는가? | 시뮬레이션 샌드박스 | 요청 보내기, 장애 일으키기, 시간 진행 같은 이벤트 버튼 | 상태·대기열·로그가 정한 규칙대로 바뀜 | 같은 조작이면 같은 결과가 나와야 한다. 무작위를 쓰면 시드를 고정한다. |
| 상태는 어떤 이벤트로만 바뀌는가? | 상태 기계 놀이터 | 현재 상태에서 가능한 이벤트 선택 | 전이 화살표 강조. 불가능한 이벤트는 이유와 함께 비활성 | 스펙의 상태표와 같은 이름을 쓴다. |
| 독자가 흔히 잘못 예상하는 부분은? | 예측 후 공개 | 답을 고르거나 값을 예상 | 실제 결과와 예상의 차이 | 점수를 매기는 퀴즈로 만들지 않는다. |
| 이 코드 줄은 그림의 어디에 해당하는가? | 코드·도식 연동 | 코드 줄 또는 도식 요소 선택 | 대응하는 쪽을 함께 강조 | 실제 파일·심볼 이름을 쓴다. |
| 실제 데이터에서 어떤 경향이 보이는가? | 필터·정렬·브러싱 | 범위 선택, 범주 필터 | 연결된 차트와 표가 함께 걸러짐 | 실제 데이터에만 쓴다. 출처와 단위를 적는다. |
| 무엇이 먼저 일어나고 무엇을 기다리는가? | 단계 탐색·유한 재생·시나리오 전환 | 이전·다음, 재생, 시나리오 선택 | 현재 단계와 이동 방향 | 템플릿의 `.mechanism` 예시가 이 패턴이다. |

## 한 문서 안의 다양성

- 장면마다 질문이 다르면 패턴도 다르게 고른다. 모든 그림에 같은 재생 버튼이나 단계 도구줄을 붙이지 않는다.
- 인터랙션 장면의 개수는 조작으로 답할 질문의 개수로 정한다. 정적 그림으로 충분한 장면은 정적으로 둔다.
- 패턴이 달라도 조작 언어는 맞춘다. 같은 뜻의 동작에는 같은 아이콘·위치·피드백을 쓴다. 예를 들어 초기화는 문서 전체에서 같은 아이콘을 쓴다.
- 같은 질문을 두 가지 조작으로 다시 묻지 않는다.
- 시각 형식도 장면의 질문에 맞춘다. 형식은 [도표·도식 레퍼런스](diagrams-and-infographics.md)에서 고른다.

## 공통 구현 계약

모든 패턴에 적용한다.

- **상태 하나에서 그린다**: 조작은 상태 값만 바꾼다. 그림·라벨·상태 문구·컨트롤은 `render(state)` 같은 한 함수가 함께 갱신한다. 그래야 그림과 설명이 어긋나지 않는다.
- **바로 반응한다**: 조작한 직후 그림이 바뀐다. 계산이 많으면 `requestAnimationFrame`으로 모아서 그린다. 한 프레임 안에서 레이아웃을 읽고 쓰기를 반복하지 않는다.
- **첫 화면과 초기화**: 처음 화면만으로 핵심을 읽을 수 있게 한다. 조작한 장면은 첫 화면으로 되돌릴 수 있어야 한다.
- **기본 입력 요소**: 값은 `input type="range"`·`input type="number"`로, 선택은 `button`·`select`·라디오 버튼으로 받는다. 끌어 놓기에는 방향키 같은 키보드 대안을 둔다. 호버로 여는 정보는 포커스와 탭으로도 연다.
- **결과 알림**: 결과 문구는 `aria-live="polite"`로 알린다. 슬라이더처럼 빠르게 바뀌는 값은 조작이 멈춘 뒤에 알린다. 움직이는 장식 요소는 접근성 트리에서 숨긴다.
- **움직임**: 기본 모드에서는 상태 전환을 보여주는 데 목적이 있는 움직임을 쓴다. 값 보간, 위치 이동, 강조의 이동은 독자가 무엇이 바뀌었는지 따라가게 한다. 목적 없는 장식 움직임과 자동 반복은 피한다. `prefers-reduced-motion: reduce`이면 큰 이동·확대·시차 효과·자동 재생을 멈추거나 짧은 페이드로 바꾼다. 바뀐 내용은 최종 상태와 강조, 상태 문구로 바로 보여준다. 실행 중에 바뀐 설정도 반영한다.
- **비동기 취소**: 재생·전환 중에 조작이 바뀌면 이전 작업을 취소한다. 세대 번호 같은 값으로 확인해 오래된 완료 처리가 새 상태를 덮지 않게 한다.
- **화면 크기**: 좌표를 쓰는 그림은 크기가 바뀌면 다시 계산한다. 모바일에서 끌기 조작이 페이지 스크롤과 부딪치지 않게 `touch-action`을 정한다.
- **근거 있는 결과**: 계산·시뮬레이션 결과는 문서에서 정한 규칙의 결과다. 실제 성능이나 처리량처럼 쓰지 않는다. 가정과 규칙을 캡션에 적는다.
- **외부 의존 없음**: 바닐라 JavaScript, SVG, CSS로 만든다. Canvas는 요소가 많아 SVG가 느릴 때만 쓰고, 같은 내용을 텍스트로도 제공한다.

## 예시 구현: 요청·기록·응답

템플릿의 `.mechanism`은 실제 서비스가 아니라 요청·기록·응답의 관계를 보여주는 개념 모형이다. 실제 지연 시간이나 저장 엔진의 보장 범위를 뜻하지 않는다. 템플릿을 고치거나 같은 패턴을 재사용할 때 아래 계약을 지킨다.

| 단계 | 정상 흐름 | 기록 실패 |
| --- | --- | --- |
| 0 | 요청을 보내기 전 | 요청을 보내기 전 |
| 1 | 요청이 대기열에 들어감 | 요청이 대기열에 들어감 |
| 2 | 기록 완료 | 기록하지 못함 |
| 3 | 성공 응답이 요청자에게 돌아옴 | 오류 응답이 요청자에게 돌아옴 |

- 단계 2가 끝나기 전에 성공 응답을 표시하지 않는다.
- 재생은 현재 단계부터 끝까지 한 번 진행한다. 마지막 단계에서 재생하면 처음부터 시작한다.
- 일시정지는 현재 이동을 멈춘다. 재개는 같은 이동을 이어 간다.
- 이전·다음은 이동을 취소하고 선택한 정적 단계로 간다. 끝에서는 다음, 시작에서는 이전을 비활성화한다.
- 다시 시작과 시나리오 변경은 진행 중인 이동을 취소한다. 시나리오 변경은 단계 0으로 돌아간다. 자동 재시도는 구현하지 않고 결과의 차이만 설명한다.
- `render()`는 단계 라벨·설명·버튼 상태를, `run()`은 유한 재생과 일시정지·재개를, `stop()`은 Web Animation 취소와 재생 세대 변경을 맡는다. `stepTo()`는 정적 단계 선택을, `setScenario()`는 정상·실패 전환을 맡는다.
- `prefers-reduced-motion`이 켜지면 재생을 멈추고 이동 버튼을 숨긴다. 이전·다음과 상태 설명은 남긴다.
- 화면 크기가 바뀌면 진행 중인 이동을 취소하고 완료된 단계는 유지한다. 다음 재생은 바뀐 노드 위치를 다시 읽는다.

## 확인 시나리오

실제 브라우저에서 모든 인터랙션 장면을 확인한다.

1. 조작한 결과가 설계 순서에 적은 결론 문장과 맞는다.
2. 첫 화면만으로 핵심을 읽을 수 있다.
3. 키보드만으로 모든 조작을 할 수 있다. 호버로 여는 정보가 포커스와 탭으로도 열린다.
4. 빠른 연속 조작과 초기화 뒤에도 그림과 상태 문구가 일치한다.
5. 움직임 줄이기 설정에서 같은 내용을 확인할 수 있다.
6. 모바일에서 조작 영역이 44×44px 이상이고, 끌기 조작이 스크롤과 부딪치지 않는다.

템플릿의 요청·기록·응답 예시를 쓰면 다음도 확인한다.

1. 정상 재생은 기록 완료 뒤 성공 응답으로, 기록 실패 재생은 오류 응답으로 끝난다.
2. 이동 중에 일시정지하면 위치가 멈추고, 재개하면 끝까지 진행한다.
3. 재생 중에 초기화하거나 시나리오를 바꾼 뒤 이전 완료 문구가 나타나지 않는다.
4. 이전·다음을 빠르게 눌러도 단계 범위를 벗어나지 않는다.
5. 모바일의 세로 노드 배치에서도 요청·응답 방향과 라벨이 유지된다.
